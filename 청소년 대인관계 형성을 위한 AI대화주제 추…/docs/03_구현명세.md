## 기술 스택

- **기술 설정**: Next.js와 TypeScript로 화면과 서버 기능을 함께 만들고, Tailwind CSS로 스타일을 입히고, Supabase로 데이터·인증·파일 저장을 처리하고, Vercel로 배포합니다. 비개발자·학생이 AI 코딩 에이전트와 함께 빠르게 MVP를 완성하기에 가장 무난한 조합입니다.
- **로그인**: 별도 로그인 없이 누구나 바로 이용할 수 있게 합니다.
- **배포**: 지금 단계에서는 외부 배포 없이 내 컴퓨터에서만 실행해 확인합니다.
- **만드는 목적**: 이 서비스는 시연·발표를 목적으로 만들어, 결제·복잡한 권한 같은 운영 요소는 최대한 가볍게 갑니다.
- **이용 역할**: 서비스를 실제로 이용하는 일반 이용자입니다.
- **운영자 로그인**: 운영자도 이용자와 같은 로그인 방식을 그대로 씁니다.
- **결제 방식**: 이 서비스는 결제 없이 무료로 이용합니다.

## 구조

Next.js App Router 기준으로 /app에 화면(라우트)별 폴더를, /components에 여러 화면이 함께 쓰는 요소를, /lib에 데이터·로직을 둡니다. 화면이 늘어나도 같은 규칙을 따르면 구조가 흐트러지지 않습니다. 다른 프레임워크를 골랐다면 같은 원칙(화면 단위·공용 요소·데이터 로직을 각각의 폴더로 분리)을 그 프레임워크의 관례에 맞게 적용합니다.

## 화면 명세

### 1. 홈 화면

- 목적: 서비스에 처음 들어왔을 때 무엇을 할 수 있는지 보여준다
- 핵심 정보: 서비스 소개, 핵심 행동으로 가는 진입점, 추천·인기 항목 일부
- Primary Action: 핵심 행동으로 이동 — 예: [검색하기]·[둘러보기]·[시작하기]
- Secondary Action: 로그인·내 정보로 이동
- Loading: 카드 모양의 스켈레톤으로 로딩 중임을 보여준다
- Empty: 보여줄 항목이 아직 없으면 '첫 항목이 곧 채워집니다' 안내로 대신한다
- Error: '불러오지 못했습니다. 다시 시도'와 [다시 시도] 버튼을 보여준다
- 이동 규칙: 핵심 행동을 누르면 목록·검색 화면으로, 로그인을 누르면 로그인 화면으로 이동한다

### 2. 입력·신청 화면

- 목적: 핵심 행동을 완료하는 데 필요한 정보를 받는다
- 핵심 정보: 입력 필드(날짜·수량·연락처 등), 선택한 대상 요약
- Primary Action: [확정]·[신청하기]·[결제하기] — 필수 입력이 모두 채워지고 형식이 올바를 때만 활성화
- Secondary Action: 이전 화면으로 돌아가기
- Loading: 제출 중에는 Primary Action 버튼을 비활성화하고 처리 중임을 보여준다
- Empty: 해당 없음
- Error: '입력값을 확인해 주세요'와 문제 있는 항목별 안내를 보여준다
- 이동 규칙: 제출이 성공하면 완료 화면으로 이동하고, 실패하면 입력값을 지우지 않고 이 화면에 머문다
- 관련 기능: 결과물 생성

### 3. 상세 화면

- 목적: 하나의 대상을 자세히 보여주고 다음 행동을 결정하게 한다
- 핵심 정보: 이름·설명·이미지, 조건이나 가격, 후기·진행 상태 같은 관련 정보
- Primary Action: 이 대상에 대한 핵심 행동 버튼 — 예: [예약하기]·[구매하기]·[신청하기]
- Secondary Action: 저장·공유·문의
- Loading: 제목·이미지·본문 자리에 스켈레톤을 보여준다
- Empty: 해당 없음 — 상세 화면은 이미 선택된 대상이 있어야 진입한다
- Error: '정보를 불러오지 못했습니다'와 [목록으로 돌아가기]를 보여준다
- 이동 규칙: Primary Action을 완료하면 입력·신청 화면으로, 뒤로 가면 목록 화면으로 이동한다
- 관련 기능: 결과 확인, 생성 히스토리

## 핵심 플로우

이 서비스의 핵심 행동은 정보 확인하기입니다. 이 흐름을 완성하는 입력·신청 화면의 Primary Action은 그 화면에 필요한 필수 입력이 전부 채워지고 형식이 올바를 때만 활성화됩니다 — 조건이 빠졌으면 버튼을 누를 수 없는 대신, 무엇이 비었는지 안내가 함께 보여야 합니다(§34 이해 가능한 폼 오류).

## API

- `POST /api/{entity}` — 입력·신청 화면에서 제출한 내용으로 새 항목을 만든다.
- `GET /api/{entity}/:id` — 항목 하나의 자세한 정보를 돌려준다. 상세 화면이 이 API를 쓴다.

## 공통 UI

모든 화면은 375px 너비의 좁은 모바일 화면에서도 가로 스크롤이나 잘림 없이 동작해야 합니다. 로딩 중에는 스켈레톤이나 스피너로, 데이터가 없을 때는 안내 문구와 다음 행동으로, 오류가 났을 때는 원인 설명과 다시 시도 버튼으로 응답합니다. 이 기준은 화면 명세의 Loading·Empty·Error 슬롯에도 화면마다 반복되며, 여기서는 전체 화면에 공통으로 적용되는 원칙만 한 번에 정리합니다.

## 반응형

레이아웃은 375px(모바일)부터 시작해 화면이 넓어질수록 여백과 배치를 넓혀가는 방식(모바일 우선)으로 만듭니다. 터치 대상은 최소 44px를 확보합니다.

## 상태 처리

화면마다 데이터를 불러오는 동안(Loading), 데이터가 없을 때(Empty), 요청이 실패했을 때(Error) 3가지 상태를 구분해서 처리합니다. 이 3가지 중 어디에도 해당하지 않을 때만 실제 내용을 보여줍니다. 상태를 구분하지 않고 빈 화면이나 깨진 화면을 그대로 보여주지 않는 것이 원칙입니다.

## Acceptance Criteria

### 1. 생성 기능 AC

- 조건: 이용자가 필수 입력을 모두 채웠을 때
- 행동: Primary Action(제출) 버튼을 누르면
- 기대 결과: 새 항목이 만들어지고 완료 화면으로 이동하며, 목록·내역에서 방금 만든 항목을 확인할 수 있다
- 확인 방법: 제출 후 완료 화면 전환을 확인하고, 새로고침한 목록·내역에도 그 항목이 남아 있는지 다시 확인한다
- 관련 기능: 결과물 생성

### 2. 검색·조회 기능 AC

- 조건: 이용자가 목록·검색 화면에 있을 때
- 행동: 조건을 입력하거나 필터를 바꾸면
- 기대 결과: 조건에 맞는 항목 목록이 화면에 바로 반영된다
- 확인 방법: 테스트 조건으로 검색해 결과 개수와 내용이 조건과 일치하는지 눈으로 확인한다
- 관련 기능: 결과 확인, 생성 히스토리

### 3. 모바일 375px 대응

- 조건: 375px 너비(대표 모바일 화면)에서 이 화면을 열었을 때
- 행동: 화면을 스크롤하거나 조작하면
- 기대 결과: 가로 스크롤이나 잘림 없이 모든 내용과 버튼을 사용할 수 있다
- 확인 방법: 브라우저 개발자 도구로 375px 너비로 맞추고 처음부터 끝까지 눌러 확인한다

### 4. Loading 상태

- 조건: 데이터를 불러오는 중일 때
- 행동: 화면이 아직 응답을 기다리고 있으면
- 기대 결과: 빈 화면이 아니라 로딩 중임을 알려주는 표시(스켈레톤·스피너 등)가 보인다
- 확인 방법: 네트워크를 느리게 설정하거나 새로고침 직후 화면을 확인한다

### 5. Empty 상태

- 조건: 표시할 데이터가 하나도 없을 때
- 행동: 그 화면에 들어가면
- 기대 결과: 빈 화면 대신 상황을 설명하고 다음 행동을 안내하는 문구가 보인다
- 확인 방법: 데이터가 없는 상태(신규 계정 등)로 화면에 들어가 확인한다

### 6. Error 상태

- 조건: 요청이 실패하거나 오류가 발생했을 때
- 행동: 그 상황이 벌어지면
- 기대 결과: 무엇이 잘못됐는지와 다음에 무엇을 할 수 있는지(다시 시도 등)가 안내된다
- 확인 방법: 네트워크를 끊거나 잘못된 값을 보내 오류를 강제로 발생시켜 확인한다

### 7. Primary Action 동작

- 조건: 각 화면의 Primary Action(가장 중요한 버튼)을 눌렀을 때
- 행동: 조건이 충족된 상태에서 클릭하면
- 기대 결과: 명세된 다음 화면 또는 상태로 정확히 이동·반영된다
- 확인 방법: 각 화면의 Primary Action을 실제로 눌러 명세된 동작과 일치하는지 확인한다

### 8. 콘솔 무오류

- 조건: 어떤 화면을 열거나 조작하고 있을 때
- 행동: 일반적인 사용 흐름을 따라가면
- 기대 결과: 브라우저 개발자 도구 콘솔에 오류(에러)가 출력되지 않는다
- 확인 방법: 개발자 도구 콘솔을 열어둔 채로 주요 화면과 동작을 한 번씩 실행해 확인한다

### 9. 새로고침 후 정상 동작

- 조건: 어떤 화면에서 작업하던 중 새로고침했을 때
- 행동: 페이지가 다시 로드되면
- 기대 결과: 입력하거나 저장한 내용이 유실되지 않고, 화면이 오류 없이 다시 정상적으로 뜬다
- 확인 방법: 주요 화면에서 값을 입력·저장한 뒤 새로고침해 내용이 유지되는지 확인한다

### 10. 이해 가능한 폼 오류

- 조건: 입력값이 형식에 맞지 않거나 필수값이 비어 있을 때
- 행동: 제출을 시도하면
- 기대 결과: 어떤 항목이 왜 잘못됐는지 이용자가 이해할 수 있는 문구로 안내된다
- 확인 방법: 일부러 빈 값이나 잘못된 형식을 입력해 제출해 보고 안내 문구를 확인한다
